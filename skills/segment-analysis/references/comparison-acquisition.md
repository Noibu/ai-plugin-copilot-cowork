# Acquire comparisons before presenting

A comparison label is not evidence that prior data was queried. For a comparative full report, obtain the actual current and immediately preceding equal-length prior periods, with matched domain/cohort, page or group, device, percentile and normalized units. Query independent current/prior requests together in a parallel batch and await both before building the report. Use the tool's currently discovered schema and measured response; do not invent historical fields or fallback numbers.

Technical performance defaults to current 30 days versus the immediately preceding 30 days. Query whole-window p75 LCP, INP and CLS per matched page/group/device using the actual `noibu_get_page_visits` aggregate schema (`input` string JSON with `periodOptions.dateTimeRange.startTime/endTime`, `queryInput` measures such as QUANTILE_75 and actual filters/groupBy). Use explicit whole windows, not the average of daily p75 buckets. A DAY trend is context, not a pooled p75. Normalize ms/score and disclose sample/visit coverage. Explicit user-requested snapshot is the only exception to attempted paired acquisition for a technical performance report.

The active-error survey retains its own seven-day window and >10 events plus last occurrence within 48 hours for merchant active-fix candidates. Where actual current schema supports it, attempt the matched prior seven-day query separately: `noibu_get_error_trends` advertises currentInterval CURRENT/PREVIOUS, timePeriod ONE_WEEK, issueIds, domainId and integer steps. Confirm returned cohort/windows before using the history. Do not claim history unsupported without checking/attempting the advertised route. Missing/failed prior data needs the exact reason after the attempt, not zero or guessed history.

Store Pulse, checkout and product comparative full reports likewise fetch current/prior per their requested window/intent. For segment analysis, current-window country/channel rankings and equal-half device diagnostics stay distinct from a prior-period comparison; retain both labelled scopes when trend intent requires prior-period data. A/B/accessibility do not invent a prior audit/experiment; paired acquisition applies when their requested evidence includes a temporal comparison.

## Renderer contract (display only — not a gate)

Acquiring both periods is a QUERY requirement above; the renderer never blocks a card over comparison metadata.
- Absent `comparison`: the card renders; the footer says comparison scope was not supplied. Label-only `{mode,label}`: the footer shows the label; KPI/funnel/finding deltas carry the measured comparison.
- Simplified block: `{mode,label,currentWindow?,priorWindow?,metrics?:[{metric,cohort,percentile?,unit,current,prior,currentCoverage?,priorCoverage?}],priorUnavailableReason?}` renders a Current vs previous period section. Values are measured finite numbers or `null` (shown as Not measured, never 0); the renderer calculates deltas. Windows, when given, are exact timezone-aware `{start,end}`, current = report window, prior = the equal-length window right before it. Vitals use p75 with ms (LCP, INP) or score (CLS), and a vital's current value must equal its performance finding.
- Receipt form (optional): add `acquisition:{requested,performed,unavailable,queries:[{metric,cohort,percentile,unit,period,window,status,source,reason?}],reason?}` as produced by the adapter below; it is checked as before and shows acquisition state in Details.
- Explicit user snapshot: `mode:"snapshot"` with `acquisition:{requested:false,performed:false,unavailable:false,queries:[],reason:"User explicitly requested snapshot ..."}`, or simply a truthful snapshot label. No prior metrics in a snapshot.
- Anything malformed or incomplete in these details (missing receipts, window mismatch, duplicates, value mismatch, unknown fields): only the comparison section is left out, with a short plain-language in-card note saying prior-period details were not shown and why. No prior value is filled in.

The local [paired acquisition adapter](../scripts/comparison_acquisition.py) is optional transparent standard-library code. `paired_requests(window,metric_specs)` produces equal preceding requests. `await acquire_pairs(async_query,window,metric_specs)` starts all sides together and returns this contract only after all results. The caller's async_query must translate requests to the discovered tool schema, query each WHOLE period, and return `{value,coverage,source}` or `{unavailable:true,reason,source}` from actual evidence. It does not discover tools, query a store, average quantiles or authorize actions. Native denial/refusal/suspension is never a retry opportunity. Retain full raw evidence independently of display sanitization.

The generic async adapter is only for ordinary async callbacks/pure offline mocks; NEVER fan out aether_tools journaled calls with asyncio, threads or subprocesses. Issue independent Noibu reads through the host’s supported parallel tool turn, or consume paired_requests deterministically in RunScript under its journal rules, then join both results before presentation. Offline callback concurrency tests are not evidence of live MCP integration or real data acquisition.

Reader-facing windows use concise dates/timezone without fractional-second clutter. Exact ISO boundaries remain unchanged in the contract/query receipts/raw evidence. Acquisition fields are supplied evidence, not proof that the renderer executed a query; the controller/recorded actual tool results establish that provenance.
