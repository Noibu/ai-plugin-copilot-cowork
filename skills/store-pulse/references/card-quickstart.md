## Terminal response policy

- `status:rendered`, `response_policy:CARD_THEN_NEXT_STEP`, `allow_text_fallback:false` is the host acknowledgement. After the card, only the next-step question ([UX guidelines](ux-guidelines.md) section 3): no recap, data replay, failed-display claim, second render or client-visibility confirmation gate. `display_confirmed:false` remains truthful and must NOT trigger fallback. The runner accepts only documented ToolResult payload/raw data envelope/text-JSON carrying explicit `status:rendered`; a card file, success boolean or completed envelope alone is not acknowledgement. Optional post-ack logging failure cannot revoke the receipt.
- Without `--candidates`, the runner also returns `priorityOptions`: the card's priorities in card order, each `{priority, findingId, label, description, onCard}`. Build the next-step question from them (labels and descriptions as given, up to 5; name any others in the question text). If it is empty, use the skill's drill-downs from its SKILL.md Output section. Accessibility audits use their own option set.
- Explicit dependency/import/read/build/render failure permits an honest concise measured fallback. START with the runner's `fallback_lead` sentence (the visual card could not be built or displayed, and the actual reason), then the fallback, preserving the exact stage/error and current/prior/window/coverage, priorities/evidence/next actions. Do not mask actual errors. Dependency failures do not prove a ZIP member is absent or a particular tenant cause. Then the next-step question.
- `status:unknown`, `response_policy:UNKNOWN_NO_REPLAY`, `allow_text_fallback:false` means delivery is uncertain, NOT failed. No whole-data replay or retry; a short uncertainty notice without duplicating the report is permitted, then the next-step question.
- Native denial/refusal/suspension: respect the host decision. Do not retry or route around it.

The summary → card → next-step question shape applies to report completion, not to prerequisite questions, errors, separate user-requested action confirmations or document-first business context/setup. Screenshot showing a card then failure prose does not identify the original raw runtime shape/cause; envelope/text normalization and post-ack logging are defensive fixes, not a proven incident diagnosis.

## Data and action boundaries

Display sanitation removes only unresolved runtime citation/session tokens; raw report/evidence and verified reader links remain intact. Keep numbers, units, thresholds, critical windows, uncertainty and ordinary provenance. Low-volume vendor monitors belong in Evidence & coverage, not padded priority cards absent a material justification; preserve merchant active-fix >10 seven-day events and last seen within 48h.

Follow local [browser readiness](browser-readiness.md) only when a browser step is needed; continue nonbrowser work while blocked. Report display never installs/connects a browser. For actions, explicitly load querying-noibu-data and read its current returned runtime/action guidance; linked sibling markdown alone is not executable materialization. Missing guidance/integration yields a precise blocker or explicitly unsaved draft, never a write. Scheduled Email always needs chat confirmation of the final exact recipient list EVEN IF supplied. Repository provider 0/1/multi selection and native approvals remain unchanged. No report authorizes sends, schedules, repository changes, tickets, status writes or automatic remediation.

## Copy-ready report shape

A SHAPE, not evidence: replace every EXAMPLE value with measured results, or drop the field. It renders as written, which the release tests check. Optional `comparison` forms: absent (footer says no scope was supplied); `{mode,label}`; or `{mode,label,currentWindow?,priorWindow?,metrics?:[{metric,cohort,percentile?,unit,current,prior,currentCoverage?,priorCoverage?}],priorUnavailableReason?}`. Use `null`, never 0, for an unmeasured value.
