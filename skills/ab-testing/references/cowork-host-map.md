# Claude design → Microsoft 365 Copilot Cowork: the host map

The skill was designed for Claude (Cowork in the Claude desktop app). This file is the single place that says what each Claude mechanism became here. Every other file in this skill is already written for Cowork; read this only to understand a difference, never to re-introduce a Claude tool.

| Claude design | Cowork | Limitation / honesty rule |
| --- | --- | --- |
| `show_widget` choice cards with `sendPrompt` buttons: goal card, pages card, pick-an-existing-test card (4b), run-mode card, follow-up cards | One `AskUserQuestion` per decision (`header` ≤12 characters, 2–5 options, labels of five words or fewer with a one-line description, no catch-all option). Exact payloads: `choice-cards.md` | Free text is always possible, so a typed answer is matched like a click. More than five choices: the top ones are options and the rest are named in the question text |
| Findings card (show_widget, one block per test, two buttons) | Adaptive Card from `scripts/show_card.py` with `abView: findings`: one block per test, followed by one `AskUserQuestion` (Preview test N · Create A/B test 1) | Cowork card buttons can't post back to the chat (tenant test 2026-10-28); a choice or typed reply is the person's own message |
| Implement card (show_widget, one button, console link) | Adaptive Card `abView: implement`: draft id, flag key, reminder, an Open draft in Noibu link button; then one `AskUserQuestion` (Automate the implementation · Done for now) | Fallback without a card: one sentence + one `AskUserQuestion` |
| Per-test hosted report (Artifact publish, side panel, `mcp` capability, live "Create A/B test in Noibu" button) | (1) Adaptive Card `abView: test` rendered after a "Preview test N" reply; (2) a standalone static HTML report file built by `scripts/build_page.py`, published to the user's output files | No side panel, no live button, no URL pasted; the report tells the reader to reply "Create A/B test N" in the chat |
| "Create A/B test in Noibu" button calling the viewer's connector | The "Create A/B test N" reply, handled in chat: validate candidate + hash, `noibu_list_ab_tests` de-duplication, `noibu_create_ab_test` DRAFT only | The reply is the authorization; native approval prompts still apply |
| Claude's built-in browser (site read, mobile previews, `resize_window` mobile) and Claude in Chrome (desktop previews, `save_to_disk`) | One local Microsoft Edge through `browser_actions`: `create_tab`, `navigate_to`, `get_dom`, `get_screenshot`, `click`/`dom_click`, `type`/`dom_type`, `scroll`, `wait`, `request_browser_interaction`, `request_user_form_fill` | No page JavaScript, no CSS injection, no viewport resize or phone emulation, no downloads, no internal browser pages. Screenshots come back to the model; they are not assumed to be saved as files |
| `scripts/walkthrough/*.js` pasted into `javascript_tool` | `get_dom` (the full DOM is saved to a workspace file when the host can) parsed offline by `scripts/dom_facts.py`, plus the per-surface look in `site-validation.md` | The saved DOM format is not documented: the parser reports `formatRecognized` and falls back to text heuristics; static DOM has no visibility/layout |
| DOM/CSS injection for "after" previews | (a) On a Shopify Online Store theme, a real unpublished Noibu preview theme — only in the build half's `theme`/`full` modes; (b) otherwise a clearly labelled description of B | The finder never writes, so finder reports show "before" plus a description; never present a description as shipped |
| Mobile previews at phone size | Mobile claims marked inferred; a "narrow desktop window" shot only when the person chooses to narrow their own window, captioned as such | No phone emulation exists |
| `console.noibu.com` only in Claude in Chrome | Edge may read it only when the person is already signed in; otherwise `noibu_*` tools and `scripts/console_links.py` | Never sign in for the person |
| Setup: desktop app + Claude in Chrome | `browser-readiness.md` (Edge, Cowork open in Edge, same work account, organization browsing, first-run consent), only when a browser step is needed | Other browsers, desktop and mobile apps cannot run local browser tasks |
| `device_bash` git, `gh`/`glab`/`az` CLIs, `git format-patch` | Provider discovery (`querying-noibu-data/scripts/action_policy.py`): GitHub MCP or Azure DevOps tools; GitLab/Bitbucket only if a connector is in the tool list; otherwise a `difflib` patch file | Never merge (`merge_pull_request` is never called); never ask for a token |
| `SuggestConnectors` / `SearchMcpRegistry` connector tiles | One plain line naming the Cowork connection that would unlock the pick, asked only after the pick needs it | No tiles |
| Shopify connector `themeFilesUpsert` and the `noibu:store-preview-qa` skill | Noibu theme tools: `noibu_list_store_themes`, `noibu_start_theme_change`, `noibu_search_theme_files`, `noibu_read_theme_file`, `noibu_edit_theme_file`, `noibu_write_theme_file`, `noibu_preview_theme_change`, `noibu_discard_theme_change`, `noibu_delete_preview_theme`; a Shopify MCP only read-only (`get-shop-info`, `graphql_query`) | Never publish; never a Shopify mutation; preview themes are "Noibu preview: …"; one open theme change per store |
| `create_trigger` (`requires_local_device`), `fire_trigger`, `list_triggers` | `SetupScheduledPrompt` / `GetScheduledPrompts` / `EditScheduledPrompt` per `querying-noibu-data/references/scheduling-delivery.md` | A scheduled run may have no browser: the person chooses "Noibu data only" (labelled) or "Require the live-site check" (stops) |
| `SendUserMessage`, `SendUserFile` | Chat text; files published to output with the host's file tools (`CopyArtifact` with the output surface) | Never paste file paths or URLs as the deliverable |
| `TaskCreate` / `TaskUpdate` | Same names, when available; optional | Skip silently when absent |
| `ToolSearch select:` | The host's deferred-tool search, to load schemas (the `noibu_create_ab_test` schema is the metric catalogue) | Read schemas; never call a tool just to read it |
| `/noibu:ab-testing` slash command in button prompts | The skill is invoked by its description or by name; replies are plain phrases | Replies never name internal files or fields |
