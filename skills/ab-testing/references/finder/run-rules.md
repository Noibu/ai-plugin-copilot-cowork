# Finder half: what it produces, prerequisites, and the rules that govern the run

Read this (with `browser.md`, `goal-and-readiness.md` and `phases.md`, plus `references/noibu-query-battery.md`, `references/site-validation.md` and `references/choice-cards.md`, all in one message) when the finder route starts — the "Look for new opportunities" or "Create a specific test" option of card 4a in SKILL.md. Block 1 (rule 1 below) goes in the message after those reads.

Where the finder's references cite a section by name ("The browser", "Block 2", "Multi-market stores", "Phase 4", "quiet-mode rule 6"), they mean these four files: "The browser" is `browser.md`; "Block 2" and the goal question are `goal-and-readiness.md`; the phases and "Multi-market stores" are `phases.md`; the quiet-mode rules are below.

Produce a short list of A/B test recommendations for an ecommerce store, aimed at the goal the merchant cares about, that the merchant can read, look at and create in Noibu. The bar for inclusion is high: every recommendation must be supported by measured Noibu data AND, when a browser is available, checked against the live site. Fewer, better-supported tests beat a long speculative list.

The deliverable is one standalone report file per recommended test (`references/output-format.md`), never written into the conversation. Each report opens with the run's intro and then its one test: what to change, why the data supports it, the variation next to the current site where a capture exists (`references/preview.md`), the setup exactly as Noibu will receive it, how much traffic its success metric sees, dev notes, and how to create it (reply "Create A/B test N"). The reports are built by `scripts/build_page.py` from a `page.json` you write, so the run's job is the content, not the HTML. Next to the reports the build writes `candidates.json` (`references/handoffs/candidates.md`): the same tests in machine-readable shape, with the selectors and evidence the build half needs.

After the reports, the same tests are summarized in the chat as the **findings card** (`references/findings-card.md`): one Adaptive Card, one block per test with what to change, why, and "Reply with: Preview test N · Create A/B test N"; once a draft exists, the implement card offers "Automate the implementation N". Their inputs are written by the same script, so they never disagree with the reports. The reports stay the full record.

The finder route ends at the card. Writing the variation code, building a preview theme and QA belong to the build half (SKILL.md, Stage 1b onward), which consumes `candidates.json`; the finder never opens a codebase, and nothing it sends offers to. The build half starts in one of two ways: after "Look for new opportunities", an "Automate the implementation N" reply (once the draft exists) picks the test (SKILL.md, "Entering with the test already picked"); after "Create a specific test", SKILL.md continues from Stage 1 step 3 with the one test, with no second question.

Why this exists: analytics data alone produces recommendations that die on contact with the site (proposing a feature that already exists, calling a working feature broken, missing copy that contradicts policy). The live-site and documentation phases kill those errors before they reach the reader. Expect validation to eliminate 1 to 3 data-derived candidates; that is the skill working. A goal exists because "here are three tests that move add to cart rate" is a decision the merchant can act on. A readiness check exists because a domain with no traffic, or without the events the goal's metric counts, cannot be tested.

**Call metadata:** on every `noibu_*` call pass `skill: "ab-testing"` and a short `skillStep` (see the `querying-noibu-data` skill).

## Speed and quiet-mode rules (read first, these govern the whole run)

The run is measured in round trips, not tool calls. Every call that does not depend on an earlier result goes in the same message as its siblings. Target shape, one message per step: Block 1 (setup, which loads the create-test schema the metric catalogue is read from) → Block 2 (goal question + resolve + the browser check) → readiness → Block 3 (Batch 1 + the homepage read) → Block 4 (Batch 2 + the goal's surfaces + the Phase 3–5 references) → the before looks → write `page.json`, build → the findings card. Anything that adds a serial step needs a reason.

1. **Batch the startup.** Block 1, in ONE message: load the `querying-noibu-data` skill by name, and load every deferred tool schema the run needs in ONE deferred-tool search: the Noibu tools `noibu_get_domain`, `noibu_list_domains`, `noibu_check_data_connection`, `noibu_get_business_context`, `noibu_search_sessions`, `noibu_get_page_visits`, `noibu_list_priority_errors`, `noibu_list_ab_tests`, plus `noibu_create_ab_test`, whose schema is the metric catalogue (and which a "Create A/B test N" reply may later ask this chat to call); the browser tool `browser_actions` when present; `AskUserQuestion`; `RunScript` and `render_ui` for the cards; and `TaskCreate`/`TaskUpdate` when present (if they are not returned, skip the task list silently). Tools a search loads can be called only from the next message, so the goal question and task creation wait for Block 2.
2. **Two query batches, maximum.** Run the battery in `references/noibu-query-battery.md` as two parallel batches ("Battery shape" in `phases.md`). The readiness reads are four small reads that decide whether the battery runs at all. One extra follow-up query only when a batch result is uninterpretable without it. Do not explore.
3. **The site read rides in the query blocks.** It never owns a block: Batch A (homepage and policy pages, which need no data) goes in the Block 3 message with Batch 1; Batch B (the goal's surfaces, at the URLs Batch 1 names) in the Block 4 message with Batch 2. Which surfaces, and whether the cart path runs, is the goal table in `references/site-validation.md`. Each page is `navigate_to` (its own call) then one `get_dom` + `get_screenshot` call; `create_tab`/`navigate_to` can't be batched with other actions, so pages run as consecutive calls in the same message.
4. **No rendering tools.** Do NOT call `noibu_visualize_page_visits` or `noibu_show_session_replay`. Get scroll behavior from QUANTILES(MAX_SCROLL_DEPTH_RATIO) and clicks from CLICKED_TEXT queries instead. Exception: the user explicitly asks for a heatmap or replay.
5. **No narration.** Don't summarize between tool calls, don't paste query results, findings or tables into the chat, don't describe what you are about to do. The only visible process is the task list, when there is one. Mark a task complete inside whatever message you send next. Write one sentence in chat only for a blocker, or when readiness stops the run (Block 2).
6. **Report-only output.** The report files are not published during the run; each goes to the person's output files only on its "Preview test N" reply (or, at the end of an unattended run, all of them in rank order). Never paste a URL or path and never reproduce the recommendations in chat. The run ends with one message holding the findings card, with no text before or after it. Everything worth telling the person goes on every report as `page.json` `caveats` footer lines, one short line each, only when it applies (never how many candidates were considered, killed or made the cut — those go in `run.killed`): whether Edge read the site, or that no browser did (structural claims inferred, previews missing), with the suggestion to run again with Cowork open in Microsoft Edge so the store can be read; when the cart path ran, that one item was added and that one line removed again; that mobile claims are inferred (no phone-size capture in Cowork) whenever a test is mobile; the goal defaulted to "All goals"; thin traffic (Noibu's days-to-verdict estimate at setup decides); recent data not arriving (R1); the store serves several markets and the reports are written for the top one; no business context saved (`build-business-context` would sharpen the hypotheses); the browser was served a localized storefront most traffic does not see; a scheduled run without a live-site check. The one thing said in chat is a change to what the person asked for that they'd otherwise miss: the goal was switched (checkout runs on another domain, or the chosen metric is not measurable here) — one plain sentence before the findings card, nothing else.
7. **Read each reference once, in a message that is already going out.** `noibu-query-battery.md`, `site-validation.md` and `choice-cards.md` in the route's first message with the four finder files; `output-format.md`, `preview.md`, `create-drafts.md` (metric rules and mapping table), `findings-card.md` and `card-quickstart.md` in the Block 4 message; `handoffs/candidates.md` never during a run (the build script writes `candidates.json`); `references/shared/*` never (the build half reads them). After a context compaction, re-open only the file the current phase needs.

## Prerequisites

- The Noibu connector. Load the `querying-noibu-data` skill before the first `noibu_*` call: orderBy requirement, row caps (sessions 100 rows, page visits 1,500 rows), measure-uniqueness rules, domain resolution, and the rule to check sibling domains before reporting a zero. This skill cites them; it does not restate them.
- A browser for the live-site read and the before looks: the person's local Edge (`browser.md`). If none is available, the run still completes: run the data phase, mark every unvalidated structural claim as inferred — never silently skip validation — and put the "run with Cowork open in Edge" suggestion in a footer line.
- A domain name or UUID from the user. If neither is given, resolve with `noibu_list_domains` and use the result; don't stall.

Who runs it: anyone with read access to the domain in Noibu. The run changes nothing in the Noibu account. On the store its only effect is the cart round trip for cart and checkout goals: one in-stock item added through the page's own control and that one line removed again, so the cart returns to what it held before (the person's own Edge cart may already hold items, which are never touched); the add shows up in the store's analytics and a footer line says so. It never fills a checkout field or places an order. Its other writes are the report files and the draft a person creates with a "Create A/B test N" reply. Building a test needs the merchant's repository and platform connections; the finder never asks for them (the build half does, in Stage 1 step 6).

Shared references (`references/shared/`) are read by the build half only.
