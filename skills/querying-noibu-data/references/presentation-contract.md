# Presentation input contract

`schema: "noibu.presentation/1"`; fields accepted by [the renderer](../scripts/build_presentation.py):

- `host`: optional `"cowork"` (default) or `"copilot-chat"`. It selects which actions the board shows: Copilot Chat agents get no schedule action, **Prepare for Copilot Pages** instead of a OneDrive save, and draft-only ticket/patch buttons. It never changes data or validation.
- `reportId`: unique lowercase alphanumeric/hyphen report identity. Use a new ID for a refreshed snapshot so prior buttons cannot silently target different evidence.
- `workflow`: one of the bundled skill names; `domain: {name, id?}` (UUID when supplied).
- `window: {start, end, label?}` and `generatedAt`: real timezone-aware timestamps. Explain comparison windows in summary/tables. A recurring schedule must derive fresh periods at run time, not reuse these fixed dates.
- `summary`: short measured conclusion, not claims invented to decorate the report.
- `overviewNotes`: optional segment-analysis-only array of up to three nonempty strings, at most 1,000 characters each. These are escaped, visible Data notes inside the Overview, not hidden under Show more. Use only measured material attribution/reconciliation/currency caveats. They do not replace the original evidence/caveats or authorize filtering or writes. Other workflows reject this field.
- `overviewContext`: optional measured population/context line (up to 1,000 characters) above analytics metrics, e.g. sessions and cart reach. Does not compute or imply a population; omit if unavailable.
- `kpis`: up to eight `{label, value, detail?, change?, tone?, changeDirection?}` objects, with formatted values and explicit units/currency. Null/unmeasured is not zero. Keep denominators/coverage in `detail`. Optional `tone` is `favorable`, `unfavorable`, or `neutral`, based on business meaning. For a verified comparison supply `changeDirection: "up" | "down" | "flat"` with a nonempty measured `change`; down renders orange independently of tone. This indicates a numeric decline, not proof of harm. Retain ↑/↓ or an explicit signed delta and units; color is supplementary. Missing comparators have no direction/change. Legacy tone-only inputs still work; no direction is inferred from formatted text.
- `funnel`: `{label, count, prior?, display?, detail?, change?, tone?, changeDirection?}`; counts are distinct nonnegative integer sessions or null. Outside checkout, display/geometry/annotations retain the existing contract and count scale. Checkout additionally accepts typed `role` (added-to-cart / checkout-started / payment-submitted / order-completed), or the exact canonical labels from [funnel presentation](funnel-visualization.md). Cart must be first, roles unique and ordered; do not guess from arbitrary labels. Checkout overrides model display/change/direction/tone and recomputes `rate`/`priorRate`: first headline COUNT with explicit positive-base 100% note, later headlines and geometry 100 × stage / SAME-period cart. Prior series uses its own cart denominator; signed pp deltas require valid current AND prior rates. `funnelBasis` is checkout-only computed output `{kind, current, prior, currentCoverage, priorCoverage, stageOrder, note, checkoutCompletion, completionInMetrics}`, never trusted incoming denominator evidence. Computed completion replaces an existing labelled completion KPI/highlight; if absent it renders separately in the funnel without adding to or dropping items from a full metric array. No null→0, divide-by-zero or invented ratios/comparisons; rising/above-100% observations are not clamped and have explicit coverage. Exact raw counts for every stage remain under Show exact counts in HTML, full Adaptive AND compact. Checkout completion is separately completed / started checkout, never the cart-to-order rate.
- `funnelContext`: optional short description of coverage, exact comparison periods and express-checkout limitations. Outside checkout it retains its existing caption behavior. Checkout's calculated denominator/coverage note is authoritative; legacy `funnelContext` is preserved only in expandable Source funnel notes, explicitly labelled annotations whose denominator does not override the calculated basis. Do not describe an unverified causal drop-off.
- `highlights`: up to six `{label, value, detail?, change?, tone?, changeDirection?}` measured overview facts (e.g. mobile CVR, top product, top collection, or median order value). Changes follow the same rules as KPIs. Do not repeat the same KPI or invent facts to fill a grid.
- Funnel stages accept `changeDirection` under the KPI comparison rules outside checkout. An unmeasured count cannot have a direction. Checkout stage rate deltas/geometry are recomputed from verified counts and own-period cart denominators, never formatted strings; missing prior removes unverified changes. No grouped-chart `valueFormat` is used; the numeric percent axis/title and yMax ≥100 (or above measured overflow) declare the basis.
- `tables`: up to eight `{title, columns: [...], rows: [[...]], kind?, note?, numericColumns?}`; at most fifty rows each. Default `kind: "table"` uses clean horizontal dividers and right-aligned numeric columns; `numericColumns` optionally lists zero-based numeric column indices. `kind: "bars"` requires exactly two columns, a label and a nonnegative numeric value or null; use it for measured payment/delivery counts. Numeric strings must be normalized before a bar chart; null is not zero. `note` declares population/units, e.g. "Completed orders only · orders". Use supporting tables for experiment details and accessibility evidence not repeated in overview facts.
- `findings`: up to twelve `{id, title, evidence, impact?, fix?, issueId?, category?, tag?}`. `tag` is a short factual display label such as "Device gap" or "Low add-to-cart rate"; it does not change action routing. Optional category is merchant/performance/vendor/accessibility; vendor adds Prepare vendor message, never automatic sending. Use actual finding IDs. Only actual Noibu issue IDs support Ignore; an accessibility selector/rule is not a Noibu issue. Full triage typically uses fewer findings as specified in the topical skill.
- Tables additionally accept `placement: "overview" | "supporting"`. For checkout, explicitly overview-placed non-bar tables appear after highlights (use for supported abandonment); bar tables default to the side-by-side mix area; remaining tables default to expandable supporting data. Explicit supporting bars remain supporting. Placement never changes populations or data. Product reports choose up to two overview-placed tables (otherwise the first two not explicitly supporting) under Show more/Show less; other tables remain in additional supporting data. Five rows are shown per expanded table with full rows retained under Show all. Segment reports similarly reveal up to three overview-placed country/channel tables (otherwise the first three not explicitly supporting), with five-row previews and all source rows retained. Remaining tables are further expandable. Other workflows retain their existing table order. Checkout findings show automatic Priority N plus any factual tag; `fix` is labelled Next check and should contain the specific investigation and verification, not an unsupported causal claim.
- `caveats`: clear evidence/coverage limitations; `timezone`: optional user-confirmed IANA timezone to prefill the schedule form.
- Tables optionally accept `barColumn`: the zero-based index of a non-label count column for product/segment-report inline bars. Values in that column must be normalized nonnegative integers or null, never formatted numeric strings, rates or inferred totals. Bars share the maximum across that table's full rows; zero remains zero and unknown has no bar. Formatting adds thousands separators without altering the source counts. Product names may visually truncate with their full escaped label available through the host tooltip/accessibility text. All source rows remain in the expandable report/export. Product `fix` text appears under Investigation & verification, while evidence and its material caveats remain visible. Product and segment reports show their first three findings, with further actual cards in More opportunities; IDs/actions are preserved.
- Findings additionally accept `performance` and `noibuLinks`. For category performance, use `{metric, value, unit, percentile, page?, pageGroup?, device?, traffic?, status?}`. Metric is INP/LCP/CLS; value is a normalized finite nonnegative number or null; unit is ms for INP/LCP and score for CLS; percentile is p75. Never pass seconds into ms fields, numeric strings or averages as p75. Null is unmeasured, without a marker/classification. `traffic: {count, unit}` uses an actual nonnegative integer/null and pageviews/visits/sessions/samples as measured, not assumed affected users. Optional status is explicitly observed; omit unknown Active status. Page/group/device and report window describe the cohort. Marker scales are linear from zero to twice the poor threshold, stable per metric, with exact values and visible overflow disclosure. Cutoffs: INP 200/500 ms, LCP 2500/4000 ms, CLS 0.1/0.25; equality belongs to the lower band. Text/labels convey meaning independently of color.
- `noibuLinks` at report or finding level: up to eight `{label, url, source}`. Source identifies the actual result or documented route plus verified IDs, not a tool instruction. Follow [console link policy](console-urls.md), including matching domain/resource and successful-write provenance. The renderer rejects non-HTTPS, non-console, cross-domain or credential-bearing URLs but cannot verify object existence/access. Omit missing links. Metric-overview links do not preserve page/date filters. Replay URLs on another supported host remain in narrative using returned jazzUrl, not this console-only field.
- `capabilities`: optional booleans `createDraft`, `ignoreIssue`, `draftPr`, `persistContext`, plus legacy `createTicket` accepted for compatibility. Set gated capabilities from real tools/authorization, not assumptions; false/missing omits those gated actions. **Open a Ticket is not gated by createTicket**: it remains visible for technical/performance/accessibility findings and resolves its integration after the destination question. Missing tools can yield an explicitly unsaved draft, never a claim that a PR/ticket exists.
- `contextHash`: SHA-256 of the exact reviewed UTF-8 Markdown, required to enable the context approval action. Do not normalize the document after hashing without generating a new approval view.

**Copy budget (display fields).** Reports are scanned in about 15 seconds, so keep display text short and put methodology in `caveats`:

- `summary`: one or two sentences naming what moved.
- `overviewContext`, `funnelContext`, table `note`, `overviewNotes`: one short line each (≤ 120 characters), such as sessions and cart reach.
- KPI `label`: the metric name only ("Conversion", "AOV"); KPI `value`: one number in one currency (put other currencies in `detail`).
- KPI and highlight `detail`: the denominator only, such as "53,212 sessions" or "8,104 / 1,909,575". Cards show it under **Details & definitions**, not on the tile.
- Finding `impact`: a short chip (≤ 32 characters, such as "~4,200 sessions affected").
- Finding `evidence`: one sentence with the key number and the move versus the prior window.

Never put citation or reference tags (for example "(ref: NB-…)"), "Source: …" provenance sentences, tool or request IDs, raw field names (`CHECKOUT_COMPLETED`), full ISO timestamps or formulas in display fields. Write the window as "Sep 28 – Oct 28, 2026 (UTC)", and put definitions in `caveats`. Nothing material is dropped: it moves to caveats or the finding's `fix`.

Do not put customer identifiers, cookies, tokens, full HTTP payloads, hidden private metadata, executable HTML, free-form prompts, or credentials in this input. HTML snippets needed as audit evidence are displayed as escaped text.

Save report to OneDrive retains kind save-report with fixed route `onedrive-document` and completion `document-saved-or-specific-blocker`. It cannot silently become a file download or an app. Download Report retains export-report. These names do not broaden authorization.

Open a Ticket retains create-ticket with fixed route ticket-destination-first and a chat-question chooser. The renderer supplies “Where should the ticket go?” and Linear/Jira/GitHub Issues/Notion as presentation hints, not an already selected provider or create permission. Read [ticket handoff](ticket-handoff.md); wait for the actual submitted answer, then discover the chosen connection/target. No response, a preselected option or Skip/cancel creates nothing. The question appears in the conversation; an all-four-choice text question is always valid.

Accessibility findings optionally declare ownership merchant-code/merchant-content/vendor/unknown. Ownership is an evidence-based handoff hint, not proof of repository access. The audit footer adds Auto-draft PR and Auto-create tickets for up to three explicitly titled actual finding IDs, retaining draft-pr/create-ticket kinds with `target.findingIds`. It omits empty batches and excludes known vendor/content-only items from PR batches. Unknown ownership requires verification after clicking. Incomplete/needs-verification checks must not be put in findings merely to enable buttons. Follow [audit remediation](../../accessibility-audit/references/remediation-actions.md); a batch never expands to all report findings or creates at render time.

`auditLayout` is optional and accessibility-only: summary-actions (default from the deliverables builder) suppresses the empty overview and repeated detailed finding cards, leaving the scoped remediation panel with the normalized summary INSIDE the card and the real PDF attachment. Detailed retains the full board. Finding evidence/IDs remain in the report input for verification. Limited review mode must remain visible; neither layout changes the underlying evidence or scan counts.

For A/B boards (`workflow: "ab-testing"`; the 21.1.x id `ab-test-opportunity-finder` remains accepted for older reports, schedules and handoffs), pass the actual validated `noibu.ab-candidates/3` (or legacy `/2`) file separately with `--candidates`. Optional `abView` (A/B workflow with candidates only): `{kind: "findings", liveSiteCheck?}`, `{kind: "test", rank, reportFile?}` or `{kind: "implement", rank, draftId (numeric Noibu test id), flagKey, state: "created"|"existing"}` selects the ab-testing skill's findings, per-test report or implement card (reply hints Preview test N / Create A/B test N / Automate the implementation N); without it the legacy candidate cards render unchanged. The `ab-testing` skill's `scripts/build_page.py` writes these inputs; never author them by hand. Domain and window must match. Buttons carry rank/title and the SHA-256 of canonical createInput JSON, not guessed selectors or an unreviewed payload. Hash encoding: sorted object keys, compact separators, UTF-8, Unicode preserved. The handler revalidates the original file and payload before writing.

The rendered board is an evidence snapshot; never treat it as live. There is no saved-dashboard or private-app action (UX guidelines: no dashboards).

Action envelopes may include `execution`, a fixed renderer-owned routing hint, not a presentation input field or free-form prompt. Technical Investigate and merchant-owned Get fix / Prepare draft PR use `repository-source` (legacy `github-source` remains accepted) with read-only inspection and connection/repository resolution; vendor findings omit that hint. These hints grant no additional authorization; the conversation handler validates the original evidence and follows its trusted workflow.

Schedule actions use the fixed `cowork-scheduled-prompt` route: discover actual send/write capability, resolve destinations and confirm schedule creation separately from delivery. The shared picker sends `schedule: {frequency, time, timezone, detail, outputs, weekday?, startDate?, monthday?}`. Frequency is weekly/biweekly/monthly, with daily additionally offered only by Store Pulse; daily has no weekday/startDate/monthday and runs every calendar day in the confirmed timezone; weekday is a full English weekday for weekly/biweekly, startDate is the matching YYYY-MM-DD first-run date for biweekly, and monthday is 1–28 for monthly. Each `outputs` entry is `{delivery, destination?, provider?}` with delivery email/teams/slack/notion/cowork/connected-app. A provider/account hint is up to 100 characters and a destination hint up to 300; neither allows control characters. A missing destination is a pending conversational choice, never permission to guess or create a schedule. No output is preselected. Older boards may send the legacy `schedule: {frequency, time, timezone, detail, delivery, weekday?, destination?, provider?}`; never accept both shapes at once. One analysis per run feeds all selected outputs; never silently omit an unavailable output or send during setup.

### Mandatory action gates (all entry paths)

The fixed `execution` metadata is a policy hint, never evidence of confirmation. For Email selected anywhere, recipient state starts `pending-chat-confirmation`: ask for exact recipient email(s), resolve names through people lookup and ask chat confirmation of the final explicit list EVEN IF addresses were supplied. Never default to the signed-in user from a checkbox; explicit “me” still needs final address confirmation. No schedule/send until confirmed; persist only the confirmed addresses in the self-contained scheduled prompt. Reconfirm changes, then honor actual scheduler/send/unattended approval gates.

Repository/CI actions follow the provider-neutral handoff, discovering actual applicable connected GitHub AND Azure DevOps accounts before choosing: zero eligible → ask whether to connect; one → reuse automatically with a read-only scope check; multiple → ask which account/provider. Deduplicate duplicate tool surfaces for the same provider/account, not distinct accounts. Read, PR, ticket and pipeline capabilities are separate.
